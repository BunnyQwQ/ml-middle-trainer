# ML Middle Trainer

Персональный сайт-тренажёр для подготовки к уровню middle ML-инженера: интерактивная
теория, задачи с тестирующей системой в духе ejudge, симуляторы и интервальные повторения.
Весь контент на русском и английском.

Только синтетические данные и публичные знания.

---

## Запуск локально

```bash
npm install
npm run dev
```

Откроется на `http://localhost:5173`. Node 20+.

### Проверки (то же самое гоняется в CI)

```bash
npm run verify
```

Это по очереди:

| `npm test` | логика сайта: вердикты, сравнение результатов, повторения, экспорт/импорт, переключение языка |

## Как перенести на другой ноутбук

Три независимых способа, выбирай любой.

**1. Сайт.** После пуша в `main` GitHub Actions собирает и публикует на GitHub Pages.
Открыл ссылку — работает, ставить ничего не надо. Прогресс лежит в IndexedDB этого
браузера; чтобы перенести его, используй экспорт/импорт JSON в настройках.

**2. Офлайн.** На сайте зарегистрирован service worker с runtime-кэшем. После одного
online-визита работают и страницы, и WASM-рантаймы (DuckDB, Pyodide) — то есть тренажёр
открывается без сети и ставится на телефон как приложение.

**3. Автономная папка.** Собрать и унести с собой:

```bash
npm run build
```

Копируешь на флешку `dist/`, `serve.mjs` и `serve.cmd` (на Windows) или `serve.sh`.
На другой машине запускаешь `serve.cmd` и открываешь `http://localhost:4173`.
Либо из репозитория: `npm run serve:dist`.

> Открыть `dist/index.html` двойным кликом не получится: браузеры запрещают WebAssembly и
> воркеры по `file://`, а на них держатся SQL- и Python-движки. Поэтому нужен локальный
> сервер — `serve.mjs` не имеет зависимостей и запускается одной командой.

Сборка использует `base: './'` и `HashRouter`, поэтому одинаково работает на GitHub Pages
в подпапке, на любом другом статическом хостинге и из локальной папки.

## Как устроена карта

Дерево последовательное, но не линейное. Узлы сгруппированы в пять актов, акты идут строго
по порядку, а внутри акта параллельно открыты две-три ветки — выбор всегда есть, но он
ограничен.

Между актами стоят **испытания** — большие практические узлы, в которые сходятся все ветки
предыдущего акта и из которых выходят ветки следующего. Каждое испытание смешивает типы
заданий (SQL по логам, Python, поиск бага, разбор кейса) и проверяет не отдельную тему,
а то, что от них осталось вместе:

| Акт | Содержание | Испытание на выходе |
| --- | --- | --- |
| I — Фундамент | распределения, ЦПТ, интервалы; выборки и группировки в SQL | «Первый отчёт»: посчитать метрику по логам, оценить неопределённость, ответить продакту |
| II — Эксперименты | гипотезы и критерии; оконные функции и сессии; устройство A/B | «Эксперимент целиком»: SRM, метрики по группам, корректная дисперсия, вердикт |
| III — Качество и решения | ловушки экспериментов, метрики качества поиска, выбор метрики | «Запуск ранжирования»: выбрать метрики, измерить качество, решить между интерливингом и A/B |
| IV — Специализации | реклама, retrieval, бандиты, классификация запросов, продовые тесты | «Инцидент в проде»: найти просевший сегмент, пересобрать порог, поймать train/serving skew, решить, что откатывать |
| V — Инженер целиком | ML system design и продуктовое мышление | «От постановки до решения»: метрики, базовая линия по логам, деньги, правило выкатки кодом и тесты на него |

Ветки четвёртого акта — боковые: они открываются после третьего испытания **или** по
достижении уровня (6 для рекламы и retrieval, 7 для бандитов и классификации, 5 для
мини-веток). Это единственная лазейка в последовательности, и сделана она намеренно: если
захочется заглянуть в отдельную область раньше, прокачка это позволит, не ломая основную
линию. В пятом акте лазейки нет: финал открывается только работой.

Каждое испытание — контест на время: 40 минут на первое, 60 на финал. Часы запускаются
кнопкой и не останавливаются при закрытой вкладке; без них задания тоже решаются, просто
попытка не засчитывается как попытка на время.

Правила проверяются в CI: пререквизит не может жить в более позднем акте, у каждого акта
ровно одно испытание, испытание обязано тянуть пререквизиты минимум из двух веток и
смешивать минимум три типа заданий, а `unlockLevel` допустим только там, где есть что
обходить.

| Zustand + IndexedDB | прогресс; при недоступном хранилище откат на localStorage, затем в память, всё в try/catch |

## Формат контента

Весь контент — это типизированные TS-модули, а не JSON или MDX. Двуязычность
обеспечивается типом, так что забытый перевод не компилируется:

```ts
type L = { ru: string; en: string; same?: true };

l('Текст', 'Text')              // обычная пара
same('impressions LEFT JOIN clicks')  // одинаково в обоих языках намеренно
```

`same()` нужен для SQL-фрагментов и идентификаторов: без него проверка контента
ругается на одинаковые ru и en как на забытый перевод.

Узел описывается так:

```ts
export const statsCi: SkillNode = {
  id: 'stats.ci',            // id задач обязан начинаться с id узла
  branch: 'stats',
  tier: 3,                   // глубина внутри ветки, определяет раскладку карты
  title: l('Доверительные интервалы', 'Confidence intervals'),
  blurb: l('…', '…'),
  requires: ['stats.clt'],   // пререквизиты, можно из других веток
  theory: [ /* блоки */ ],
  tasks: [ /* задачи */ ],
  sources: [{ title: '…', url: 'https://…' }],
};
```

### Блоки теории

`p` · `h` · `note` (`info` / `warn` / `key`) · `list` · `formula` (KaTeX) ·
`code` · `table` · `sim`.

У каждого абзаца автоматически появляется кнопка перевода, раскрывающая второй язык
прямо под ним. Блок `sim` вставляет интерактив по id из `src/content/sims.ts`:

```ts
{ type: 'sim', sim: 'ci-coverage', title: l('…','…'), caption: l('…','…') }
```

Проверка контента требует хотя бы один интерактивный блок в каждом узле.

### Как добавить задачу

**Квиз** (`single` / `multi` / `number`):

```ts
{
  kind: 'quiz',
  id: 'stats.ci.q-interpretation',
  mode: 'single',
  prompt: l('…', '…'),
  choices: [{ id: 'a', text: l('…', '…') }, …],
  correct: ['b'],
  explanation: l('…', '…'),
}
```

Для `mode: 'number'` вместо `choices` указываются `value` и `tolerance`.

**SQL.** Задача ссылается на открытый датасет и на скрытые. Эталон не хранится как
«ожидаемый ответ» — он исполняется на тех же базах, что и твой запрос:

```ts
{
  kind: 'sql',
  id: 'stats.distributions.sql-queries-per-user',
  prompt: l('…', '…'),
  dataset: 'search-sample',
  hiddenDatasets: ['search-hidden-1', 'search-hidden-2'],
  starter: '…',
  reference: 'WITH per_user AS (…) SELECT … ORDER BY q',
  orderMatters: true,
  writeup: l('…', '…'),
  clickhouse: { code: '…', note: l('…', '…') },
}
```

Вердикты: `OK`, `WA` (с показом расхождения на открытом тесте), `RE`, `TL`.
На скрытых тестах показывается только форма расхождения, без данных.

**Python.** Функция плюс скрытые тесты. `sampleTests` показываются пользователю,
`tests` — нет:

```ts
{
  kind: 'python',
  id: 'stats.ci.py-wilson',
  signature: 'def wilson_interval(successes: int, n: int, z: float = 1.96) -> tuple[float, float]:',
  starter: '…', reference: '…',
  sampleTests: 'assert …', tests: 'assert …',
  writeup: l('…', '…'),
}
```

**Выбор метрики.** Продуктовый сценарий, общий пул метрик и три слота: оффлайн, онлайн
и guardrails. Для слота может подходить несколько метрик, поэтому проверка принимает
любой защитимый вариант, а после ответа показывает разбор по каждой метрике из пула:

```ts
{
  kind: 'metric-pick',
  id: 'metric.basics.pick-ads',
  area: l('…', '…'),
  scenario: l('…', '…'),
  guardrailCount: 2,
  options: [
    { id: 'logloss', label: l('…','…'), correctFor: ['offline'], note: l('…','…') },
    { id: 'auc',     label: l('…','…'), correctFor: [],          note: l('…','…') },
  ],
  writeup: l('…', '…'),
}
```

Эти задачи собираются в отдельный режим на `/#/metrics` — там они показаны все вместе,
независимо от ветки, и решённое там засчитывается в родной узел.

**Свои тесты (мутационная проверка).** Обратная задача: даётся корректная реализация и
несколько сломанных версий, а писать надо тесты. Вердикт OK только если набор проходит на
эталоне и падает на каждом мутанте — то есть тесты не просто зелёные, а что-то ловят:

```ts
{
  kind: 'write-tests',
  id: 'testing.basics.write-topk',
  prompt: l('…', '…'),
  reference: 'def top_k(scores, k): …',
  mutants: [
    { id: 'no-tiebreak', label: l('…', '…'), code: 'def top_k(scores, k): …' },
    …
  ],
  starter: '# assert …',
  referenceTests: 'assert …',
  writeup: l('…', '…'),
}
```

`check:py` гоняет каждую такую задачу дважды: `referenceTests` обязаны поймать всех мутантов,
а `starter` — не поймать, иначе задача ничему не учит.

Ещё есть `case` (открытый ответ, затем эталон, чек-лист, честная самооценка — «упустил
существенное» ставит кейс на повторение — и необязательный `writeup` про то, чем сильный
ответ отличается от слабого) и `findbug` (указать строку).

**Питоновские пакеты.** Задача может попросить пакет из сборки Pyodide:
`packages: ['pandas']`. Общий для нескольких задач код выносится в `preamble` — он
выполняется до решения и до тестов, так что все задачи ветки стартуют от одинаковых данных.
Первый запуск такой задачи дольше: колесо качается с CDN и кладётся в кэш (в офлайне — из
кэша PWA, в CI — из `node_modules`).

### Испытания как контесты

Узел с `boss: true` закрывает акт, и у него есть `contest: { minutes }`. Часы считаются от
сохранённого времени старта, а не таймером в React: перезагрузка, смена языка и закрытая
вкладка минут не добавляют. Решённым в попытке считается задание, у которого последняя
успешная отправка позже старта забега, поэтому «пройти заранее, потом включить часы» не
работает. По истечении времени забег закрывается сам, задания остаются доступны как
практика. Хранится лучшая попытка: сначала по числу решённых, при равенстве — по времени.

### Правила на контент, которые держит CI

- У каждого блока есть `ru` и `en`, оба непустые и не совпадающие дословно.
- id узлов и задач уникальны; id задачи начинается с id узла.
- Пререквизиты существуют, циклов нет.
- У квиза правильный ответ есть среди вариантов; у `single` он ровно один.
- У SQL-задачи есть скрытые тесты, эталон непустой, стартер не равен эталону,
  а при `orderMatters` в эталоне есть `ORDER BY`.
- Эталон SQL реально исполняется на всех базах и даёт непустой результат;
  запрос неверной формы и те же строки в обратном порядке проверкой отклоняются.
- Эталон Python проходит скрытые тесты, а незаполненный стартер — не проходит.
- У `write-tests` минимум три мутанта с разными id, ни один не совпадает с эталоном.
- Каждый акт закрыт ровно одним испытанием; узел, открывающий акт, зависит от испытания
  предыдущего; пререквизит не может жить в более позднем акте.
- Испытание смешивает минимум три типа заданий и собирает пререквизиты минимум из двух веток.
- В каждом узле есть хотя бы один интерактивный блок; исключение — узлы-практикумы
  с пятью и более задачами, где интерактив и есть сами задачи.
- Ссылки только https и только на домены из списка проверенных вручную
  (`ALLOWED_SOURCE_HOSTS` в `scripts/check-content.ts`).

### Числа в разборах

Числа в симуляторах и подписях считаются кодом от фиксированного сида, а не вписываются
руками: наклон -1/2 в ЦПТ подгоняется МНК по симулированным точкам, покрытие интервалов
измеряется прогоном, мощность проверяется Монте-Карло поверх формулы. Так текст не может
разойтись с картинкой.

## Прогресс

Звёзды за узел: 3 — все задачи с первой попытки (≥90%), 2 — ≥60%, 1 — узел пройден.
Опыт за задачи и за звёзды, уровни растут линейно. Серия дней считается по календарным дням.

Интервальные повторения: ошибка ставит карточку на завтра, дальше 1 → 3 → 7 → 14 дней,
правильный ответ на последнем интервале выпускает карточку из колоды. Карточки заводятся
на все семь типов заданий, включая кейсы с самооценкой и написание тестов.

«Повторение» — не список ссылок, а сессия: задача рендерится прямо на экране тем же
компонентом, что и в уроке (`TaskSwitch`), с тем же редактором и той же проверкой.
Очередь фиксируется на старте сессии, иначе она пересобиралась бы под руками после каждого
ответа. Результат сразу уходит в расписание: верно — карточка на следующий интервал,
неверно — назад на завтра, «Пропустить» не трогает расписание вовсе. Карточка, чьей задачи
больше нет в контенте (переименовали), молча выпадает из очереди.

Результаты испытаний хранятся отдельно от узлов: по каждому боссу текущий забег и лучший
завершённый. Экспорт/импорт — JSON с версией схемы; импорт пропускает любые данные через
нормализацию, поэтому испорченный файл не ломает приложение.

## Этапы

1. **Готово.** Каркас, деплой, двуязычность, карта уровней, прогресс с экспортом/импортом,
   тёмная тема, мобильная версия, PWA.
2. **Готово.** Ветка SQL целиком (джойны → группировки → оконные функции → сессии →
   продуктовые метрики), «Статистика» и «A/B» полностью: гипотезы и p-value, выбор критерия,
   бутстрап, подглядывание, множественные сравнения, ratio-метрики, CUPED и «Разбор
   экспериментов».
3. **Готово.** «Метрики качества поиска»: релевантность и асессорская разметка, precision/recall@k,
   MRR и MAP, DCG и nDCG, оффлайн против онлайна с позиционным смещением, интерливинг.
   Плюс тренажёр выбора метрики отдельным режимом.
4. **Готово.** Рекламное ранжирование (eCPM, GSP и VCG, калибровка pCTR, выручка против
   релевантности), Retrieval (инвертированный индекс и BM25, эмбеддинги и двухстадийная схема,
   ANN: IVF, HNSW, PQ), бандиты (eps-greedy, UCB, Thompson, нестационарность) и классификация
   запросов (дисбаланс, macro/micro F1, пороги и длинный хвост).
5. **Готово.** Продовые тесты на Python с нуля (зачем тесты вообще, что такое assert и
   фикстура, тесты на данные и на ML-пайплайн) с задачами нового типа — написать тесты и
   поймать ими сломанные версии; интервальные повторения превращены в сессию и покрывают
   все типы заданий; три мини-ветки строго по заданию: три бага в ML-коде, один квиз на
   десять вопросов по DL, десять задач на pandas.
6. **Готово.** ML system design (постановка задачи, данные и сплит, выкатка и жизнь модели
